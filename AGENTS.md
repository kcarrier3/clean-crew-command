- Employee invite emails are sent by the `invite-employee` function via Resend with an auth-only sender (separate from the billing sender) and logged in `employee_invitations`; why: delivery state and resend need one audited path.
- Missed punch-in SMS runs from the `check-missed-punches` function on a pg_cron schedule, deduped by the unique key on `sms_alert_log`; why: retries and overlapping runs must never double-text a manager.
- Accounting handoff is a one-row-per-invoice spreadsheet export built by `src/lib/billing/booksgptExport.ts`; why: the accounting system's invoice import never combines rows and has no API to push to.
- Account deletion is two-step: `request-account-deletion` re-checks the password and emails a one-time hashed link (auth sender), and `confirm-account-deletion` claims it atomically and calls the service-role-only `delete_account_for_user`; why: no client path may delete an account without password plus email proof.
- Security-definer trigger and internal-only functions get EXECUTE revoked from PUBLIC/anon/authenticated (service_role only); permission helpers used in RLS stay authenticated-only; why: nothing callable through the API should bypass access rules, and triggers fire without caller EXECUTE.
- Invoice money fields (line_total, subtotal, tax, total, credits) are computed by DB triggers; the client never computes or writes them authoritatively; credits are changed only via the credit RPCs.
- Recurring invoices are one row per schedule per period (`recurring_billing_periods`) and, when consolidated, one invoice per bill-to company, billing email, and period (`recurring_group_key`). A schedule that already has an invoice for that period is not generated again. New tax exemptions require a certificate unless `tax_exempt_certificate_missing` was set for a row that was already exempt.
- Billing access is job title only (`can_manage_billing`): Owner, Office Manager, or Operations Manager. The admin role does not grant it. Credit approval over the self-approve limit uses those same three titles (`can_approve_credits`). Contract amounts live in `job_site_financials`. Table SELECT/INSERT/UPDATE on `job_sites` and `project_phases` are revoked from the API roles and re-granted per column, excluding `contract_amount`, `billing_amount`, and `billing_percent`; a later column on those tables needs an explicit grant. Project Crew Leads mark checkpoints only on job sites they are scheduled on. A progress-billing job bills each completed checkpoint's schedule amount. Supply price writes use `can_manage_supply_pricing` (Supply Management, Owner, Office Manager, Operations Manager), not billing access. A resale supply drop-off creates a Ready to Bill event, and clearing that drop cancels the event until it is invoiced; sales tax is still applied by the invoice trigger.
- The invoice company name lives only in `COMPANY_NAME` (`supabase/functions/_shared/company.ts`), currently Summit Facilities Group. The billing From display name defaults to that name unless `BILLING_FROM_NAME` is set. Reply-to is `BILLING_REPLY_TO_EMAIL` and is left unset; when no reply-to is configured the invoice email adds “This mailbox is not monitored. Please do not reply to this email.” The billing domain has no MX record on purpose. Invoice logo and brand colors (`BRAND_ORANGE` #FF6000, black, body #1F1F1F) live in that same file. The PNG is `public/branding/summit-logo.png`; the email inlines it, and the PDF loads `INVOICE_LOGO_PATH`.
- Planning calendar access is admin role or an explicit `view_calendar` grant (`src/lib/calendarAccess.ts`), and the `calendar_drafts` RLS uses the same rule; why: the menu and the data must agree so a hidden calendar can't be reached directly.
- Estimating access is decided by public.can_estimate() and mirrored by src/lib/estimatingAccess.ts; Project Crew Leads are always denied (no admin override; a RESTRICTIVE policy on every estimating table blocks creator/owner fallbacks too); why: manager role must not leak estimating to crew leads.
